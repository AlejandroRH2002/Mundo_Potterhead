# Revisión y recuperación local — 26 de octubre de 2026

## Causa y datos preservados

Windows reserva el intervalo TCP 5358–5457, que incluye 5432. PostgreSQL estaba saludable dentro de Docker, pero el puerto no se publicaba en el host. Se recreó únicamente el servicio local en 127.0.0.1:15432 conservando el mismo volumen. No se editó el archivo privado .env ni se contactó Neon.

Con autorización expresa, se creó un pg_dump local privado y se restauró satisfactoriamente en un contenedor aislado, sin red y con almacenamiento temporal en RAM. El respaldo permanece en `.private-backups/`, excluido de Git. No se borraron volúmenes reales.

Se aplicaron localmente `20261021000000_model_inventory` y `20261026000000_sized_skus_search`. La segunda tenía un delimitador SQL `$` incorrecto: su transacción falló y se revirtió; comprobada la ausencia de ProductSku, se marcó únicamente ese intento local como rolled-back, se corrigió a `$$` y se aplicó. No se modificó una migración aplicada satisfactoriamente en este entorno. Antes de integrar, comprobar que nadie haya aplicado otra versión de esta migración en destinos compartidos; no alterar checksums allí.

El arranque local puede alinear el puerto en memoria con el publicado por el servicio Compose únicamente si usuario, contraseña y base coinciden, el destino original es loopback y no responde. No redirige producción ni destinos remotos. `pnpm dev:check` comprueba conexión y esquema sin imprimir credenciales.

## Verificaciones y controles

Instalación frozen-lockfile, lint, pruebas unitarias, build y build:web ejecutados con Node 24.22.1. Integración usa PostgreSQL temporal con tmpfs: migraciones repetibles, sesiones persistentes, roles, cookies, CORS, limitador compartido, SKU, concurrencia, historial y rollback. Se corrigió la selección de modelos agotados únicamente en enforce y se actualizaron aserciones para consultar cantidades en SKU. Capture permanece sin restricción.

HTTP local: readiness, catálogo, frontend y proxy 200; administración anónima 401. Los tests verifican login con fixtures, sin usar credenciales privadas. El control de secretos del bundle pasó. El chunk principal informa 115.67 kB gzip en la salida de Vite; no se reconstruyó una referencia histórica para atribuir un delta.

Revisión focalizada: scrypt, HMAC, cookies HttpOnly, revocación, rol activo, esquemas estrictos, consultas parametrizadas, Origin/X-Requested-With, limitador y logs acotados se conservan. No se realizó pentest completo ni inspección de la configuración real de proveedores. DB_TLS_MODE=disable sigue siendo una excepción configurable que NO debe usarse en producción; revisar el entorno de Render. No introducir HTML arbitrario ni usar el dev server con túneles públicos.

## Integración, despliegue y rollback

1. Seleccionar Node 24.22.1 y pnpm 11.21.0; el runtime portátil usado en esta revisión no cambia el Node global del equipo. Los archivos .node-version/.nvmrc, engines, CI y Docker quedan alineados. No versionar .tools.
2. Revisar la rama fix/security-node-oct-2026: también contiene el trabajo previo de inventario/tallas aún no integrado. No tratar esta PR como un parche aislado del inventario.
3. Ejecutar `pnpm install --frozen-lockfile`, `pnpm lint`, `pnpm test`, `pnpm build`, `pnpm build:web`, `pnpm audit --prod`, `pnpm audit`. En entorno con Docker, `pnpm test:integration` usa solamente su base temporal.
4. Publicar solo la rama: `git push -u origin fix/security-node-oct-2026`. Crear PR borrador hacia main con este informe y resultados; no fusionar sin revisión. La CLI gh no está instalada en este equipo; usar la web de GitHub.
5. Antes de producción: respaldar y probar restauración, revisar migraciones/checksums y ensayar en staging. Build → migraciones aprobadas con conexión directa privada → arranque. No ejecutar reset ni seed en producción. Mantener INVENTORY_MODE=capture hasta validación funcional explícita.
6. Al aprobar integración, seleccionar Node 24.22.1 también en los proveedores; un pin en Git no acredita el runtime desplegado. Verificar health/live, health/ready, login, cookies, roles, catálogo, subida de imágenes y cotización. Vigilar errores, latencia y conexiones de BD.
7. Rollback de aplicación: volver al artefacto anterior compatible con el esquema aditivo y desplegarlo; no deshacer SQL ni borrar datos. Si hace falta recuperar datos, restaurar primero en una base separada, verificarla y planificar el cambio de conexión bajo mantenimiento. Rotar secretos solo mediante procedimiento coordinado (SESSION_SECRET invalida sesiones).
